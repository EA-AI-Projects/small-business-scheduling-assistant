# SMS conversation flow and command boundary

Clients and the owner can text in plain language. The model interprets the text; the calendar changes only when a reply matches something the system itself offered. Issue [#60](https://github.com/EA-AI-Projects/small-business-scheduling-assistant/issues/60) recorded the owner decisions behind this flow. Everything below is exercised with fictional data, an in-memory calendar, and no Twilio, DynamoDB, or live SMS.

## How a conversation works

| Step | Example text | What happens |
| --- | --- | --- |
| Ask | "Hi. Do you have availability for tomorrow?" | The model resolves "tomorrow" to a date. The backend checks the 14-day horizon, holidays, working hours, and existing visits, then offers 3–5 real start times. Nothing is written. |
| Pick | "10 works", "the 10 o'clock one", "option 2", or "yes" when one time was offered | The reply must map to exactly one offered option. A pending request is created, and the reply states its full date and time and that the owner must approve it. |
| Approve | Owner: `APPROVE REF` / `DECLINE REF`, or a short plain reply ("yes", "ok", "approve it", "decline") | The exact commands always work. A plain reply acts only when it is one of the short decision replies, exactly one request is pending, no offer is open, and the model judges it a decision; inside a calendar conversation, or after the assistant asked about a request, the question must also have been sent first (see [Owner message routing](#owner-message-routing)). Anything longer or hedged gets one clarifying question and changes nothing. A bare "no" never declines. With several pending, the reply lists them and asks. |
| Cancel | "I can't make Thursday" | "Cancel your Thu Oct 1 at 9:00 AM visit? Reply YES to confirm." Only a plain yes cancels; "no" keeps the visit. If several visits match, they are listed by number; picking one ("2", "the 11 one") leads to the same YES question. |
| Reschedule | "Can I move Thursday to Friday morning?" | Replacement times are offered the same way. Picking one creates a pending replacement; the original stays confirmed until the owner approves it. "I need to reschedule" first asks which day. |

An offer or confirmation question stays valid for **30 minutes**. A later answer gets "That offer expired after 30 minutes, so nothing changed" and a prompt to ask again. Any new request replaces the previous offer.

When a specific time is open, the offer is that single time, answered with "yes". When it is not, the three nearest open times are offered instead. Offers prefer on-the-hour starts, then half-hour starts, and spread across the requested days.

## Client calendar questions

A verified client can ask about their own schedule by text (#240; PRD 6.5). The answer is read-only and built in `client_calendar_questions.py` from the client's own current visits, read for that message.

| Example text | Reply |
| --- | --- |
| "Do I have bookings this week?" | "You have 1 confirmed visit, 1 pending request from Tue Sep 29 to Sun Oct 4:" then one line per visit, such as "Thu Oct 1 at 9:00 AM-11:00 AM PDT, confirmed (ref …)" or "…, pending owner approval, not confirmed yet (ref …)". |
| "When are the cleaners coming?" | Every upcoming visit, labeled the same way. |
| "How many confirmed visits next week?" | The count, plus "You also have 1 pending request …" when one exists. |
| "Booking for Friday?" | "Do you want to check the visits you already have for Fri Oct 2, or request a new cleaning?" with an example question for each. Nothing else happens. |
| "What times are open Friday?" | Unchanged: an availability offer (see above). |

- **Recognized.** Common phrasings ("do I have", "when is my", "when are the cleaners", "how many visits", "what's on my schedule") are matched deterministically without the model, but only when every sentence is made entirely of schedule-question words. A polite lead-in ("I'm trying to find out", "I want to know", "Can you tell me") is dropped first, "I want a summary of my itinerary" counts as a summary (it covers the range just discussed) while "Show me a list of my visits" is a plain list, a count is given only when every sentence asks how many, and sentences that are only a greeting, thanks, ok, or please are ignored, so "Do I have any confirmed bookings already? I'm trying to find out when the cleaners are coming" is answered (#241 screenshot). Anything else (a second sentence such as "When is my visit? Cancel it", a change, a preference, open times like "the earliest cleaning", or an unrelated question like "How many hours is a cleaning?") goes to the normal flow. Other wording reaches the model, which may propose `calendar_question` with a day range, or `clarify_booking` when the text could mean checking or requesting; the model supplies no visit facts. The check-or-request question is asked without the model only for a short question ending in "?"; "Cleaning Friday" is still a booking request.
- **Grounded and scoped.** The answer lists only the sender's own confirmed visits and unexpired pending requests that have not ended, read for that message, so an answer after an approval, cancellation, or expiry reflects it. Other clients' visits, owner blocks, notes, and profile fields are never read into the answer. A client with more than 8 active visits gets the existing "contact the owner" reply.
- **Statuses.** Confirmed and pending are labeled separately; pending always says "not confirmed yet". A question that names one status ("confirmed", "pending", "request") filters to it but still reports the other ("You also have …"), so a pending request is never hidden or implied to be confirmed.
- **Dates.** One day or one week ("tomorrow", "Friday", "this week", "next week", a date); no day means every upcoming visit. Past days are refused, and a range starting in the past starts today. Several ranges in one text get a question asking for one. Times are in the business timezone with its abbreviation.
- **No writes, no lingering prompt.** A question creates no request, hold, or cancellation. It closes any open offer, visit list, or cancel confirmation, and the reply adds "I closed my earlier question, so nothing was booked or cancelled", so a later "yes" or number cannot act on it.
- **Follow-ups (#241).** For 30 minutes after a calendar answer, a short follow-up of range, status, and view words with a follow-up cue ("What about next week?", "And Friday?", "Just confirmed ones", "How many?", "Show all") reuses the last question's range, statuses, and list-or-count view, changing only what it names. "Summarize my itinerary" covers the range just shown, every status. Each follow-up rereads the calendar, so a visit approved, cancelled, or expired in between is shown as it is now, and every answer states its dates and statuses. Other wording reaches the model, which sees only the open range ("Last calendar answer: 2026-09-28 to 2026-10-04") and may propose `calendar_question` with a new range or none (keep the range); statuses and view carry over unless the text names them, says "how many", or asks to see the visits.
- **Requests stay requests.** A bare day ("Friday"), a clock time ("Friday 10"), or other words ("Cleaning next week please") are not follow-ups: the model reads them, so a booking request still gets an offer. A single booking noun with a day ("Booking for Friday", "Cleaning Friday instead", "What about cleaning Friday") gets the check-or-request question; "What about my visits Friday?" is a follow-up.
- **Action-like replies.** A calendar answer asks nothing, so a bare yes, no, number, or pick ("2", "the first one") right after it gets "I only listed your visits, so nothing was booked or cancelled" and how to ask for a change; the conversation stays open. A reply the model cannot read gets one question ("Should I check another day or status, or do you want to request or change a visit?") and the conversation stays open.
- **Prompt precedence.** The sender has one open prompt. A calendar question or follow-up replaces an open offer, visit list, or cancel confirmation (saying so). A new request (availability, booking, reschedule, cancel) or an exact command replaces the calendar conversation, so its offer or confirmation is the one a later reply answers. An owner counteroffer the client has not answered stays open (owner decision on #240): each calendar answer then ends with "The owner's offer of <time> is still open: reply YES to request it, or NO to turn it down". While the calendar conversation is open only a plain YES or NO (with no status word) goes to that offer; "Just the confirmed one", "1", or "the first one" is read as being about the calendar answer and never accepts it.
- **Checks.** `backend/tests/test_client_calendar_questions.py` and `test_client_calendar_followups.py` drive these cases through the conversation service with a scripted model and the in-memory calendar.

## What cannot cause a write

- **Model output never selects a write.** The model proposes an intent, a resolved day range, a time window, and the day of an existing visit. Its output is schema-validated: dates must be `YYYY-MM-DD`, times `HH:MM`, and a clarification carries no action fields. The backend rejects impossible dates, past dates, and days beyond the booking horizon before any offer.
- **Replies are matched deterministically.** A bare option number, a time ("11am", "2:30 pm", "noon"), an ordinal ("the second one"), "option N", a day name that narrows the offer ("Thursday at 8am"), or a plain "yes" for a single option. A reply containing a negation ("not 10", "can't"), a question mark, an alternative ("10 or 12"), or a change of plan ("next week", "instead") is not treated as a pick; it goes to the model, which can only offer new times or ask a question.
- **An owner counteroffer is answered the same way.** A client's plain yes to a counteroffer the owner confirmed (open 30 minutes) creates one pending request for the owner to approve; the original request stays pending until then. No, a different time, or an answer after 30 minutes creates nothing, and a new request replaces the offer. See [SCHEDULING_CONTRACTS.md](SCHEDULING_CONTRACTS.md#client-acceptance-176).
- **Numbered picks follow the offer.** When an offer lists numbered options and asks for a number, a bare whole number from 1 through the number of options selects that option, even when the same number could name an offered clock hour. A reply such as "2 PM" selects by time.
- **Ambiguous picks ask again.** "8am" is ambiguous when 8:00 AM is offered on two days. The reply asks for an option number or a time with AM or PM, and nothing is booked. A time that was not offered is refused the same way.
- **Confirmations are rechecked.** A cancellation confirmation is refused if the visit changed after the question. A replacement pick is refused if the original visit is no longer confirmed. Every booking re-checks availability transactionally, so a time taken in the meantime is reported, not double-booked.
- **The owner has no offer memory.** Only a client's own offer can be answered, and only by the phone it was sent to.
- **The #24 malformed and ambiguous cases still change nothing**, even when a fake model returns an unsafe proposal for them.

Exact commands keep working and bypass the model: `BOOK YYYY-MM-DD` (offers that day's times), `BOOK YYYY-MM-DD HH:MM`, `RESCHEDULE REF to YYYY-MM-DD[ HH:MM]`, `CANCEL REF`, `APPROVE REF`, and `DECLINE REF`. They accept one complete local date or time with no timezone suffix or alternative; the backend rejects daylight-saving gaps and ambiguous times.

## Conversation memory

The last offer, list of visits, confirmation question, or client calendar question is stored per sender phone. It holds only the offered or listed start instants, one appointment ID and version, or a calendar question's day range, statuses, and list-or-count view (never the visits it listed), plus its 30-minute expiry. It holds no message text.

- **Local harnesses** keep it in process memory; it resets on restart.
- **The cloud worker** stores it as one `SMS_STATE#<phone>` item per sender in the business table. Reads use strong consistency and enforce expiry themselves. DynamoDB TTL on `expires_at_epoch` removes stale items later; TTL deletion can lag, so it is cleanup, not the expiry check. Clearing a prompt is conditional on its ID, so an older reply cannot erase a newer offer.

## Owner message routing

One model classification decides what an owner SMS means (#177; PRD 6.3 and 6.6, owner decision 2026-10-04). The model only proposes; the backend validates every approval, decline, and offer send, and every failure asks and writes nothing. The assistant no longer answers with "Reply YES to approve or DECLINE" unless the owner asks how to approve; an unclear reply gets a focused question about the open prompt, or a short list of what the assistant can do.

Order of handling for each owner text (first match wins):

1. **Exact commands.** `APPROVE <ref>` / `DECLINE <ref>` act without the model. If an offer is open it is dropped first.
2. **Offer redelivery.** The same SMS delivered again replays its original reply and never acts twice.
3. **Offer hook (deterministic).** A plain YES sends an open offer, NO or CANCEL drops it, and a new offer instruction ("Can you offer 2:00 PM instead?") replaces it or prepares one. A finished offer absorbs a bare yes/no ("nothing was approved") for one hour while its request is still pending.
4. **Calendar questions.** The answer to an open clarifying question, then a complete calendar question, then a follow-up with no approval-like word. All are read-only.
5. **The model**, with bounded context, for everything else.

Contexts and what each allows:

- **An open counteroffer draft stays open when the owner asks a calendar question.** The question is answered, and the answer ends with "Your offer to <client> for <time> is still waiting: reply YES to send it or NO to cancel it." Nothing is cancelled silently. This is the safer choice: it never sends anything the owner did not confirm, never loses the draft, and the reminder says exactly what a YES will do. The draft still expires 30 minutes after it was prepared.
- **While a draft is open, a reply can only confirm it, cancel it, revise it, or be clarified.** It is never an approval of the countered request. An unclear reply keeps the draft and repeats the reminder. Only an exact `APPROVE <ref>` approves that request.
- **After a calendar answer with a draft open, only an unmistakable YES (yes, y, yep, yeah, yup) sends the draft.** Replies like "ok" or "confirmed please" could mean "show me the confirmed ones", so they are clarified. When the offer prompt itself was the last message, a plain yes-style reply sends it, and a model-proposed send acts only on the offer-send list: yes, y, yep, yeah, yes please, ok, okay, ok please, sure, send it, yes send it (optional "thanks"; no approve or confirm words, so "approve" asks "Reply YES to send exactly that offer, or NO to cancel it. To approve the original request, reply APPROVE <ref>."). "Go ahead" and longer replies are asked about. The deterministic plain-YES check for an open offer (from #175) runs before the model and also accepts "confirm", "confirmed" and "confirm it", ignoring repeated trailing marks ("yes!!", "yes..."), so those send the offer; the request itself is never approved by them. A model-proposed cancel ("forget it") needs a cancelling word, and cancelling sends nothing.
- **"What about 3pm instead?" right after a calendar answer is clarified.** "instead" with a time but no offer verb (offer, propose, suggest, counter) can mean "offer that time to the client" or "show me the calendar then". The assistant asks which and prepares nothing; "Offer 3pm instead" prepares the offer. With the offer prompt as the last message, the same words revise the draft.
- **A clarifying question about a request (option A, #174).** Whenever the assistant asks "Do you mean approve <client, time, ref>?", inside a calendar conversation or not, it records that request, and the record is kept for 24 hours. Only a later reply, received after that question's reply was **sent** (and within 30 minutes of the send), can approve, while that request is still the single pending one at the same version. A question that was not sent (pending, failed, or unsaved), its redelivery, or a message received before the send keeps approvals blocked and the assistant asks again, for as long as the record lives. After the 30 minutes, a plain yes still means that request only while it is the single pending one at the same version; if it was decided or another request is pending, the assistant asks again and names the current request. While the calendar conversation is open, a later calendar answer supersedes the question, and a new question replaces it. After 24 hours the record is gone and the no-question rule applies.
- **The plain-reply allowlist (owner decision, #177).** The model classifies what a text is about; it never decides on wording. A model-proposed approve, decline, or offer send acts only when the **whole reply**, trimmed, lowercased, with one trailing "." or "!" removed (so "yes..." asks, except through the offer plain-YES check above) (and an optional trailing "thanks" or "thank you"), is exactly one of the short replies in `owner_reply_classification.py` (the only place the lists live). A "?" never matches. Approve: yes, y, yep, yeah, yes please, ok, okay, ok please, sure, approve, approved, approve it, approve please, confirm, confirmed, send it, yes send it. Offer sends use the separate offer-send list above. Decline: decline, decline it, decline please, please decline, declined, reject, reject it, deny, deny it. Any other text the model judges to be a decision gets one clarifying question that names the request and the plain reply that would act ("Do you want to decline <client, time, ref>? Reply DECLINE to confirm, or APPROVE. Nothing has changed."; for an offer, "Reply YES to send exactly that offer, or NO to cancel it."). That question is the one the option A rule below counts. There are no hedge, negator, or retraction word lists: longer text is simply asked about. A bare "No" or "cancel" never declines a request (while an offer is open, "No" still cancels the offer). "confirmed" is on the list but, inside a calendar-status conversation, the model reads it as a calendar follow-up first and the existing rules apply. Known limits: replies with a reason ("Decline, I can't that day"), polite extras ("Yes, approve it", "Go ahead", "ok thanks a lot"), and any hedge are asked about instead of acting; the exact `APPROVE <ref>` / `DECLINE <ref>` commands always work. With no conversation and no question outstanding, a plain allowlist reply acts only when the model judges it a decision with high confidence and exactly one request is pending; with several pending, the reply lists them and asks for the reference.
- **Interleaved and stale prompts.** A request that arrives while a question is open changes nothing: an approval is refused unless exactly one request is pending and it is the one that was asked about. A new request that arrives after an offer draft (compared by the request's recorded creation time, never by the editable hold length; a request stored before the creation time was recorded counts as possibly newer, so every YES shows the draft again, and no offer can be sent, until that request is decided or expires) also counts as the latest message: a YES then shows the draft again ("A new request arrived after I drafted this offer, so I did not send it yet") instead of sending it, and the next YES sends. A draft past its 30 minutes, a request decided elsewhere, a lapsed or cancelled offer, and an expired calendar conversation never approve; the reply says so.
- **Backend validation, always.** The model's proposal is acted on only with high confidence, a literal match to the single pending request's reference (at least eight characters), a whole reply on the allowlist above, and the context rules above. An always-approving model cannot approve after a calendar answer, with an offer open, after a cancelled offer, for a question that was not sent, or after the pending request changed. The allowlists are the gate; no word list is used for routing decisions that act.
- **Failure.** A model error, timeout, malformed answer, low or medium confidence, or no model adapter asks one clarifying question and writes nothing; with a draft open the question repeats the draft reminder.
- **Many pending requests.** The old "contact the owner" stop for more than 8 pending requests no longer blocks owner texts. The model sees at most the first 8 pending requests; the owner can still approve any request by its exact reference, and ambiguous plain decisions list the requests and change nothing.
- **Model context** for owner texts is small and PII-minimized: today and timezone, the last assistant message kind (calendar answer, approval question, offer prompt, offer with calendar answer, closed offer, none), calendar view, range and statuses, the named request, up to 8 pending requests (ref, client first name, time), and the open offer (ref, first name, offered time). No phone numbers, addresses, full names, or history. The model can propose `approve_named_request`, `decline_named_request`, `calendar_followup`, `confirm_offer`, `cancel_offer`, `calendar_question` (answered with "which day or week?", which is stored as an open range question so a bare "next week" answers it), `how_to` (explains approve, decline by reference, and what the assistant can do; it never advertises NO as a decline), or `unclear`.

## Owner calendar questions

The verified owner can ask read-only calendar questions by text, such as "What is next week looking like?", "What clients do I have tomorrow?", or "How many bookings do we have for Friday?" (PRD 6.6). These are fixed question types in `owner_calendar_questions.py`. Complete questions and follow-ups without an approval-like word are matched deterministically, do not use the model, and cannot write. Every other owner reply is routed as described in [Owner message routing](#owner-message-routing).

- **Grounded.** Every answer is read from the calendar and client records at that moment, so a follow-up after a calendar change reflects the change. Nothing is listed that is not in the records.
- **Dates and times.** Answers name the dates and show times in the business timezone. A day runs midnight to midnight in that timezone; a block that crosses midnight appears on both days and counts once in a total.
- **Statuses.** Confirmed visits, pending requests (unexpired holds only), and unavailable blocks are labeled separately. Declined, cancelled, and expired items are not shown.
- **Counts say what they counted.** A count that names a status ("pending requests", "confirmed visits", "including pending") uses it. A bare "bookings", "visits", or "appointments" count does not state a status, and what a booking means is not assumed: the assistant asks "confirmed visits only, pending requests only, or both?" and then counts. Anything else present in the range is reported as not counted.
- **Clarifying questions.** A missing day or week, or a count with no stated status, gets one focused question. While it is open, "confirmed", "pending", or "both" answers it.
- **Approval-like replies** (for example "yes please", "confirmed", "ok thanks") inside a calendar conversation go to the model, then the backend validates; see the next section.
- **Follow-ups.** Within 30 minutes, short messages narrow or expand the last question ("just the pending ones", "what about Friday?", "how many?", "by day"). "next Friday" means the Friday of next Monday-to-Sunday week; the answer always states the date.
- **Length and MORE.** A calendar page stays within 480 characters (three GSM-7 segments) and whole entries are never cut. When an offer draft is open, the reminder is added after the page, so that reply can exceed 480 characters (never cut, and well under the 1600-character Twilio limit); when the page says "Reply MORE", a one-line reminder is used instead of the full YES/NO/APPROVE instructions so the two do not compete: the reply says "Showing 1-5 of 20. Reply MORE for the rest." MORE resumes from the stored position only if the entry list is unchanged; if the calendar changed in between it says so and restarts from the first entry, so nothing is skipped or repeated. A redelivered MORE repeats its page.
- **Daylight saving.** On the day clocks change, times carry PDT or PST so a repeated hour reads unambiguously.
- **Memory.** The last question type, date range, and status names are kept per sender for follow-ups, with no message text: in process memory locally, and as one `OWNER_QUESTION#<phone>` item in the business table in the cloud (strongly consistent reads, expiry enforced on read, TTL cleanup).

## Try it locally

For texts together with the owner web app on one shared calendar, use the text simulator described in the [README](../README.md#try-the-app-locally). The terminal exercise below has its own separate calendar.

With the backend dependencies installed as in the [README](../README.md#local-backend) and a local ignored `.env` containing `OPENAI_API_KEY`, run from the repository root:

```sh
(
  set -a
  source .env
  set +a
  cd backend
  .venv/bin/python -m scheduling.local_conversation
)
```

The subshell removes the key from the parent shell even if the command is interrupted. Use only invented messages. Recognizable phone numbers and entry/access-code phrases are rejected locally; this filter cannot detect every kind of private data.

1. As `client`, ask "Do you have anything tomorrow morning?" and reply with one of the offered times.
2. Type `/calendar` to see the pending request, then `/owner` and `yes`.
3. Switch back with `/client`, text "I can't make it tomorrow", and reply `yes`.
4. Type `/quit` to exit. The calendar and conversation memory reset on restart.

Without `OPENAI_API_KEY`, the simulator answers plain language with a question and a note; exact commands and replies to an existing offer still work.

## Profiles, privacy, and the cloud path

SMS collects only the visit date and time. The owner enters and verifies client profile fields (name, service address, and home size/duration) in the authenticated calendar. A text from a sender without an active, verified profile and matching consent is not authorized for commands. It gets no scheduling reply by SMS, the model is not called, and no scheduling change occurs. If the profile or consent changes after the text arrives, the conversation service refuses the text, and the sender recheck blocks delivery of its reply.

The model receives only the inbound text, actor, current local date and weekday, timezone, booking horizon, and up to eight short active references. It receives no profile name, phone, address, notes, or API key. Model timeouts and malformed output return a safe retry message. Messages over 1,000 characters are rejected intact.

The signed Twilio ingress can hand off a verified receipt ID to SQS after persisting it. The worker rereads the stored receipt, rechecks current consent and actor state, and uses the same conversation service as the local exercise, with the DynamoDB conversation memory above. Each SMS scheduling transaction checks STOP markers atomically with the calendar write. A cancelled transaction is terminal for that receipt, so a STOP that is later cleared cannot revive an older request. Offers, questions, and other noncommitted replies are recorded with a stable receipt-based outbox intent; the sender derives the destination from the verified receipt and rechecks consent, opt-out, and the fictional-number refusal. Committed changes are announced by the existing notification texts, which state the full date and time. Reply bodies are purged with inbound bodies 90 days after the last exchange (in the owner's own thread, 90 days after each message, #201). Duplicate webhook or queue delivery cannot create a second logical request or reply. Ingress never passes STOP, HELP, START, or UNSTOP texts to scheduling (the app's STOP words exclude CANCEL, so a bare "Cancel" is an ordinary message, matching dev's Twilio Advanced Opt-Out keywords, #91), but it honours a Twilio `OptOutType` of `START` only for the body START or UNSTOP, so a "Reply YES" answer is still read as an ordinary reply; a STOP or HELP provider tag always wins.

The AWS handoff is disabled by default. The `EnableSmsConversations` parameter only enables it when signed SMS ingress and SMS sending are also separately authorized; the worker obtains the OpenAI key from a `SecureString` at `/scheduling/<environment>/openai/api-key`. Enabling TTL on the table is part of the stack template. Deploying this code, provisioning that secret, and sending live texts require separate owner authorization.
