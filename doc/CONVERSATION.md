# SMS conversation flow and command boundary

## Recent message context (#270)

For a verified client or owner, the application can assemble an ordered rolling
24-hour transcript from its own inbound receipts and outbound provider-handoff
records. Each entry carries the sender role, send or receive time, provider ID,
and exact text. A client's history requires the same business, verified phone,
and client ID; owner history requires the same business and owner phone. Draft
outbox messages are absent until provider acceptance. The bound is 24 messages
and 12,000 characters. Older whole messages are omitted, while the newest
exchange and the latest booking invitation are preferred; an oversized message
is omitted rather than shortened. The history builder does not itself call a
model or authorize scheduling actions. The owner's thread (keyed by owner phone,
the same sent-aware records) is read for the owner tool loop as conversation
data. A history read failure produces the owner failure reply.

Clients and the owner can text in plain language. The model interprets the text; the calendar changes only when a reply matches something the system itself offered. Issue [#60](https://github.com/EA-AI-Projects/small-business-scheduling-assistant/issues/60) recorded the owner decisions behind this flow. Everything below is exercised with fictional data, an in-memory calendar, and no Twilio, DynamoDB, or live SMS.

## Scheduled booking invitations (#249)

This section specifies future owner-configured outreach; it is not active SMS behavior. The owner chooses enabled/disabled, one local weekday and time, and a lookahead of 1 or 2 weeks. A run uses the business timezone and a fixed run instant `R`; its appointment window ends at the same local wall-clock time 7 or 14 calendar days later, inclusive. If that end time does not exist, use the first valid local instant after the gap; if it occurs twice, use the first occurrence. Compare appointment instants against that window so daylight-saving changes do not shift the chosen wall-clock run time. If the configured run time does not exist on a daylight-saving transition day, skip that week's run. If it occurs twice, run once at the first occurrence. Do not backfill a skipped run. A confirmed appointment overlapping that window makes the client ineligible. A pending request does not. A cancellation removes a confirmed appointment from the current eligibility check, but never erases invitation history.

For each client, require an active profile and a current, verified phone with matching in-person SMS consent, no opt-out, and no previous invitation in `(R - lookahead, R]`. The previous invitation means the last successfully handed-off invitation, not an attempted or failed selection. Reserve one invitation per client and scheduled window with an idempotency key so retries and concurrent runs cannot duplicate it. A missed run does not backfill or send a catch-up burst; the next configured run evaluates current state. Disabling stops future selection. A day/time or lookahead change takes effect at the next run; it does not reset invitation history. If changing from two weeks to one, the one-week interval is measured from the last actual invitation at that next run.

Immediately before handing an invitation to the SMS provider, recheck the client, phone, consent, opt-out, confirmed appointments, and invitation interval against current state. A newly confirmed booking, opt-out, deactivation, or changed phone suppresses the queued text. A newly pending request still does not count as confirmed; the invitation may be sent, but it must not imply that the pending request is confirmed. If a confirmed booking is cancelled before send, the current eligibility check may permit the invitation, subject to the interval. A changed phone requires fresh in-person consent and verification before any invitation to that new number. A queued invitation must not be sent later merely because a disqualifying state subsequently clears; reselect at a future scheduled run. Record suppression without an SMS.

Examples (all run times in the business timezone): a Monday 9:00 a.m. one-week run excludes a client with a confirmed appointment at the following Monday 9:00 a.m.; a pending request at that time alone does not exclude them. If an invitation was sent on Monday at 9:00 a.m., the following Monday's 9:00 a.m. run is the earliest next eligible run, subject to the appointment and consent checks. For a two-week run, a confirmed appointment at 9:00 a.m. on the second following Monday also excludes the client; a later appointment does not. An invitation sent at 9:00 a.m. this Monday first permits another at 9:00 a.m. on the second following Monday. If the run was missed, Tuesday is not a catch-up run. If the owner changes to a two-week lookahead after Monday's invitation, the next Monday run is still inside the two-week repeat interval.

Owner-approved initial invitation (#252): “Smart Scheduling Assistant: Would you like to book a cleaning visit in the next [one/two] weeks? Reply with a day and time that works for you, or STOP to opt out.” Render the saved lookahead as “one week” or “two weeks” so the singular version reads correctly. Omit the client's name; it is not needed to invite a verified recipient and cannot become stale after queueing. The owner confirmed the current consent disclosure and approved Twilio campaign cover this proactive text; see [A2P_REGISTRATION.md](A2P_REGISTRATION.md#booking-invitations-249-252). A reply enters the existing booking conversation, where availability and owner approval still govern confirmation. The invitation itself creates no booking or hold. The implementation promotes eligible intents into the existing SMS outbox and routes replies through the ordinary inbound booking flow. The approved text is the editable default for one saved message used by both scheduled and immediate invitations. The owner may use any nonblank text up to 500 characters without a STOP-content check; onboarding provides opt-out instructions, while consent and opt-out state are still checked before delivery. Editing settings after selection suppresses that queued scheduled run. The new schedule and invitation delivery gate default to disabled. A provider attempt with uncertain acceptance stays held for operator reconciliation, preventing an automatic duplicate. Separate authorization is required before live sending.

## How a conversation works

| Step | Example text | What happens |
| --- | --- | --- |
| Ask | "Hi. Do you have availability for tomorrow?" | The model resolves "tomorrow" to a date. The backend checks the 14-day horizon, holidays, working hours, and existing visits, then offers 3–5 real start times. Nothing is written. |
| Pick | "10 works", "the 10 o'clock one", "option 2", or "yes" when one time was offered | The reply must map to exactly one offered option. A pending request is created, and the reply states its full date and time and that the owner must approve it. |
| Approve | Owner: `APPROVE REF` / `DECLINE REF`, or a plain-language decision | Exact commands still work. For other approval or decline wording, the model may inspect current pending requests and call a typed decision tool with its reference and version. The backend makes the versioned transition; an ambiguous target gets a question and no write. See [Owner approval and decline tool loop](#owner-approval-and-decline-tool-loop-298). |
| Cancel | "I can't make Thursday" | "Cancel your Thu Oct 1 at 9:00 AM visit? Reply YES to confirm." Only a yes cancels (a plain yes is matched directly; other wording is read by the model, see below); "no" keeps the visit. If several visits match, they are listed by number; picking one ("2", "the 11 one") leads to the same YES question. |
| Reschedule | "Can I move Thursday to Friday morning?" | Replacement times are offered the same way. Picking one creates a pending replacement; the original stays confirmed until the owner approves it. "I need to reschedule" first asks which day. |

**Model-read answers (#273).** Owner decision (Enrique, 2026-10-07): a free-form affirmative such as "yes please, go ahead" confirms a cancellation just as it accepts an offer, because the backend still binds one visit and version and the confirmation expires after 30 minutes. The offer-then-accept and confirm-before-write flow is unchanged, but the model reads the client's answer in any wording. After the cancel question, "please go ahead and drop it" is proposed as `confirm_cancel` and "actually let's hold onto it" as `keep_visit`; after a replacement offer, an acceptance is proposed as `request_booking` for the offered time. The model names no visit. The backend acts only on this sender's own stored, unexpired prompt (the prompt's client ID must match the sender's), which already binds one visit and its version, and the inbound receipt ID is the idempotency key. With no open question, an expired one (reply: "That confirmation expired after 30 minutes, so nothing was cancelled"), one replaced by a newer request, a visit that changed since the question, "keep it" while no cancellation is waiting (reply: "OK, nothing changed. Your visit stays booked."), a taken replacement time, or an original no longer confirmed, nothing is written. A model-proposed `cancel` for a visit that is not the sender's own cannot resolve to it. Plain YES, "no", and option numbers are still matched deterministically first. The backend's own wording (cancelled, requested move with the original still confirmed, kept, or nothing changed) is the safe result; since #283 the model may rewrite it as described under [Profiles, privacy, and the cloud path](#profiles-privacy-and-the-cloud-path), and the safe wording is what is sent when that draft is rejected.

An offer or confirmation question stays valid for **30 minutes**. A later answer gets "That offer expired after 30 minutes, so nothing changed" and a prompt to ask again. Any new request replaces the previous offer.

When a specific time is open, the offer is that single time, answered with "yes". When it is not, the three nearest open times are offered instead. Offers prefer on-the-hour starts, then half-hour starts, and spread across the requested days.

## Client calendar questions

A verified client can ask about their own schedule by text (#240, #241; PRD 6.5). The model interprets the question; the answer is read-only and built in `client_calendar_questions.py` from the client's own current visits, read for that message.

| Example text | Reply |
| --- | --- |
| "Do I have bookings this week?" | "You have 1 confirmed visit, 1 pending request from Tue Sep 29 to Sun Oct 4:" then one line per visit, such as "Thu Oct 1 at 9:00 AM-11:00 AM PDT, confirmed (ref …)" or "…, pending owner approval, not confirmed yet (ref …)". |
| "When are the cleaners coming?" | Every upcoming visit, labeled the same way. |
| "How many confirmed visits next week?" | The count, plus "You also have 1 pending request …" when one exists. |
| "Booking for Friday?" | "Do you want to check the visits you already have for Fri Oct 2, or request a new cleaning?" with an example question for each. Nothing else happens. |
| "What times are open Friday?" | Unchanged: an availability offer (see above). |

- **Interpreted by the model (owner decision, #241).** The model reads what the client means in any wording or language, including Spanish, polite lead-ins, and several sentences. It proposes `calendar_question` with a day range, the statuses asked about (confirmed, pending, or both), and list or count; or `clarify_booking` when the text could mean checking a visit or requesting one. It supplies no visit facts, and no keyword rules decide whether a text is a calendar question. Replies are in English.
- **Grounded and scoped.** The answer lists only the sender's own confirmed visits and unexpired pending requests that have not ended, read for that message, so an answer after an approval, cancellation, or expiry reflects it. Other clients' visits, owner blocks, notes, and profile fields are never read into the answer. A client with more than 8 active visits gets the existing "contact the owner" reply.
- **Statuses.** Confirmed and pending are labeled separately; pending always says "not confirmed yet". When the model reads the question as about one status, the answer filters to it but still reports the other ("You also have …"), so a pending request is never hidden or implied to be confirmed.
- **Dates.** The model resolves the day range ("tomorrow", "this week", "la próxima semana"); no range means every upcoming visit. Past days are refused, a range starting in the past starts today, and a reversed or longer than 62-day range gets a question asking which day or week. Times are in the business timezone with its abbreviation.
- **No writes, no lingering prompt.** A question creates no request, hold, or cancellation. It closes any open offer, visit list, or cancel confirmation, and the reply adds "I closed my earlier question, so nothing was booked or cancelled", so a later "yes" or number cannot act on it.
- **Follow-ups (#241).** For 30 minutes after a calendar answer, the model is told only that answer's terms ("Last calendar answer: 2026-09-28 to 2026-10-04; statuses: confirmed, pending; view: list"), never the visits. A follow-up ("What about next week?", "¿Y el viernes?", "Just confirmed ones", "How many?", "I want a summary of my itinerary") is another `calendar_question`; any status or view it leaves unset keeps the shown value, and it says whether the range is new dates, all upcoming visits, or the range shown, so "Show me all my upcoming visits" is not narrowed to the last week. Each follow-up rereads the calendar, so a visit approved, cancelled, or expired in between is shown as it is now, and every answer states its dates and statuses.
- **Requests stay requests.** During a calendar conversation the model can still read a text as a booking request ("Can I get a cleaning Friday instead?"), which gets the normal offer and replaces the calendar conversation; open-times questions keep the availability offer (owner decision on #240).
- **Action-like replies.** A calendar answer asks nothing, so a bare yes, no, number, or pick ("2", "the first one") right after it gets "I only listed your visits, so nothing was booked or cancelled" and how to ask for a change; the conversation stays open. A reply the model cannot read gets one question ("Should I check another day or status, or do you want to request or change a visit?") and the conversation stays open.
- **Prompt precedence.** The sender has one open prompt. A calendar question or follow-up replaces an open offer, visit list, or cancel confirmation (saying so). A new request (availability, booking, reschedule, cancel) or an exact command replaces the calendar conversation, so its offer or confirmation is the one a later reply answers. An owner counteroffer the client has not answered stays open (owner decision on #240): each calendar answer then ends with "The owner's offer of <time> is still open: reply YES to request it, or NO to turn it down". While the calendar conversation is open only a plain YES or NO (with no status word) goes to that offer; "Just the confirmed one", "1", or "the first one" is read as being about the calendar answer and never accepts it.
- **Checks.** `backend/tests/test_client_calendar_questions.py` and `test_client_calendar_followups.py` drive the conversation service with a scripted model standing in for the model's reading. The real model's reading is checked by the synthetic cases in `backend/evals/scheduling_messages.py` (the #241 screenshot texts, Spanish questions and follow-ups, counts, open times, and an ambiguous booking); see [MODEL_EVAL.md](MODEL_EVAL.md).

## The shipped client path (#275)

Every free-text client message follows one path: exact commands and plain YES/number replies are matched first; otherwise the model proposes one typed intent from the transcript and open prompt kind; the backend validates actor, target, date, stored prompt, and availability and performs at most one write; the model may then phrase the reply from the backend's result; the reply goes through the existing idempotent outbox. The old read-only drafter (`draft_read_reply`), which only wrapped an availability or calendar answer in a greeting, was removed because the single result-based drafter above covers those answers as well as writes.

The fixed backend sentences were kept deliberately. They are not a second conversational path: each is the validated fallback for a result (the model's first call failing, or its draft failing the length, date, time, or reference check) and the sentence a retry or redelivery replays. Exact commands, the opt-out and verified-profile gates, and the stored-prompt checks are unchanged. Nothing in this change alters which writes are possible.

Behavior checked offline with a scripted model in `backend/tests/test_conversation_flow.py`, `test_client_calendar_questions.py`, `test_sms_processing.py`, `test_sms_delivery.py`, and `test_outbox.py`: the invitation, "Oct 13 at 1 pm", then "Oct 13" sequence (an offer for the single time, then that day's openings, never a booking or "What day?"); acceptance only against the sender's own unexpired offer; unavailable, taken, past, and out-of-horizon dates; an expired or replaced offer; a model failure, timeout, or malformed or contradictory draft (the safe reply is sent, nothing else is written); STOP and opt-out (the model is never called for an opted-out sender); an over-length draft; a retried receipt or redelivered queue message (one hold, one reply); and a delivery failure (checked per component, not as one end-to-end test: the provider failure is retryable and backed off in the outbox tests, and the outbox sender never calls the conversation service, so a retry cannot schedule again). The owner decision path is described below. Live model behavior is in [MODEL_EVAL.md](MODEL_EVAL.md).

## Owner approval and decline tool loop (#298)

After owner verification and exact-command handling, an owner message enters a model tool loop. The model receives the owner's bounded, sent-aware 24-hour SMS transcript, the business-local date, and the timezone. The transcript is conversation data, not authority to perform an action. The model can call only these structured JSON tools (#299 added the calendar read; #300 added the counteroffer tools):

| Tool | Arguments | Authoritative result |
| --- | --- | --- |
| `list_pending_requests` | Empty object | Current requests for this business, with reference, version, client first name, local time, and pending status. |
| `get_calendar` | `from`, `to`, `statuses`, `offset` | Current business-scoped calendar and first-name client facts for the requested local range and page. Read-only. |
| `approve_request` | `ref`, `version` | Lifecycle approval result or a precise error. |
| `decline_request` | `ref`, `version` | Lifecycle decline result or a precise error. |
| `draft_counteroffer` | `ref`, `version`, `date`, `time`, `client_text` | A checked, stored 30-minute draft with the model's exact client-facing text and its ID; no client send. |
| `send_counteroffer` | `draft_id` | Send result for this owner's current, unexpired draft after its exact client text appeared in a sent owner preview. |
| `cancel_counteroffer` | `draft_id` | Discard result for this owner's current, unexpired draft; no client send. |

The model chooses the target and action from the owner's message and current tool result. A clear choice among several requests can act. A hedged or qualified message is interpreted in context; no fixed short-reply vocabulary or HIGH-confidence threshold gates the decision. If the target or intent remains ambiguous, the model asks a short question and does not call a decision tool. The #177 plain-reply allowlist and sent-clarification-question state no longer govern this owner approval path. Exact `APPROVE <ref>` and `DECLINE <ref>` commands still bypass the model.

The backend derives the owner and business from the verified receipt, accepts only the named tools and their strict JSON arguments, and resolves a decision only to a current pending request in that business with the supplied version. The lifecycle service checks expected version, expiry, transition, and calendar conflicts transactionally. A stale reference or version, failed call, or repeated decision cannot silently change another request. The inbound receipt ID remains the idempotency key; a duplicate receipt replays its stored reply. Required audit and notification intents enter the existing outbox with the lifecycle write. Owner identity, consent, opt-out, sender rechecks, and delivery gates remain in force.

The model writes the final owner SMS after seeing the tool result. It must describe only a successful action or say that nothing changed after an error; the backend no longer applies #285's per-entry date, time, and reference checks to this decision reply. It checks that the text is nonempty GSM-7 and at most 480 septets. If the final text is invalid, it asks the model once to rewrite it within that limit without another tool call. A second invalid answer, model failure, timeout, or unreadable history uses the fixed owner failure line. If a decision already committed, the fallback does not undo it; the persisted lifecycle and outbox result remains authoritative. No live model or SMS call is part of this change.

Calendar questions, paging, and counteroffer drafting, sending, and cancellation use the same owner tool loop. A calendar read cannot send a counteroffer or change the schedule; only `send_counteroffer` can queue the client text.

For a counteroffer (#300), the model writes `client_text` as part of `draft_counteroffer`; the backend runs the existing preparation checks and stores that exact client-facing text for a later send. The model's owner preview must show that exact text, and `send_counteroffer` requires a trusted record that this preview was sent after the draft was created. If the preview is missing, the tool returns `owner_preview_missing` and sends nothing. The model also writes the owner's later send, cancel, or error SMS from the tool result under the same GSM-7/480-septet final-reply rule. The backend does not apply a separate semantic wording check to the model's decision or draft text, so the model can misunderstand a confirmation or describe a draft inaccurately. Before send, the backend rechecks the request's pending status and version, the draft's owner and 30-minute lifetime, any newer request, client eligibility and consent, and the proposed slot. A failed or stale tool call sends no client message. The send is idempotent, and a redelivered owner receipt replays the stored reply without sending again. The client receives only the model's exact `client_text` stored with the confirmed offer through the existing outbox and sender checks. Live SMS still requires separate authorization.

## What cannot cause a write

- **Client model output does not write without backend validation.** `request_booking` (#272) is honored only for a time in the sender's own unexpired stored offer, and `confirm_cancel` (#273) only for the sender's own unexpired stored cancel confirmation. Client proposals are schema-validated: dates must be `YYYY-MM-DD`, times `HH:MM`, and a clarification carries no action fields. The backend rejects impossible dates, past dates, and days beyond the booking horizon before any offer. Owner decision tools have the separate versioned boundary above.
- **Replies are matched deterministically.** A bare option number, a time ("11am", "2:30 pm", "noon"), an ordinal ("the second one"), "option N", a day name that narrows the offer ("Thursday at 8am"), or a plain "yes" for a single option. A reply containing a negation ("not 10", "can't"), a question mark, an alternative ("10 or 12"), or a change of plan ("next week", "instead") is not treated as a pick; it goes to the model, which can offer new times, ask a question, or call `request_booking` for a time actually offered.
- **An owner counteroffer is answered the same way.** A client's plain yes to a counteroffer the owner confirmed (open 30 minutes) creates one pending request for the owner to approve; the original request stays pending until then. No, a different time, or an answer after 30 minutes creates nothing, and a new request replaces the offer. See [SCHEDULING_CONTRACTS.md](SCHEDULING_CONTRACTS.md#client-acceptance-176).
- **Numbered picks follow the offer.** When an offer lists numbered options and asks for a number, a bare whole number from 1 through the number of options selects that option, even when the same number could name an offered clock hour. A reply such as "2 PM" selects by time.
- **Ambiguous picks ask again.** "8am" is ambiguous when 8:00 AM is offered on two days. The reply asks for an option number or a time with AM or PM, and nothing is booked. A time that was not offered is refused the same way.
- **Confirmations are rechecked.** A cancellation confirmation is refused if the visit changed after the question. A replacement pick is refused if the original visit is no longer confirmed. Every booking re-checks availability transactionally, so a time taken in the meantime is reported, not double-booked.
- **The owner has no offer memory.** Only a client's own offer can be answered, and only by the phone it was sent to.
- **The #24 malformed and ambiguous cases still change nothing**, even when a fake model returns an unsafe proposal for them.

Exact commands keep working and bypass the model: `BOOK YYYY-MM-DD` (offers that day's times), `BOOK YYYY-MM-DD HH:MM`, `RESCHEDULE REF to YYYY-MM-DD[ HH:MM]`, `CANCEL REF`, `APPROVE REF`, and `DECLINE REF`. They accept one complete local date or time with no timezone suffix or alternative; the backend rejects daylight-saving gaps and ambiguous times.

## Conversation memory

The last offer, list of visits, confirmation question, or client calendar question is stored per sender phone. It holds only the offered or listed start instants, one appointment ID and version, or a calendar question's day range, statuses, and list-or-count view (never the visits it listed), plus its 30-minute expiry. It holds no message text.

- **Local harnesses** keep it in process memory; it resets on restart.
- **The cloud worker** stores it as one `SMS_STATE#<phone>` item per sender in the business table. Reads use strong consistency and enforce expiry themselves. DynamoDB TTL on `expires_at_epoch` removes stale items later; TTL deletion can lag, so it is cleanup, not the expiry check. Clearing a prompt is conditional on its ID, so an older reply cannot erase a newer offer.

## Owner message routing

The owner model uses one tool loop for pending-request decisions, calendar reads, and counteroffers. The backend keeps the stored offer safeguards for every draft and send.

Order of handling for each owner text (first match wins):

1. **Exact commands.** `APPROVE <ref>` / `DECLINE <ref>` act without the model. If an offer is open it is dropped first.
2. **Offer redelivery.** The same SMS delivered again replays its original reply and never acts twice.
3. **Owner tool loop**, with the bounded transcript, local date, timezone, and current draft details, for calendar questions, follow-ups, MORE, pending-request decisions, and counteroffer drafting, sending, or cancellation.

Contexts and what each allows:

- **Counteroffer draft.** The model interprets an owner's proposed time, reads the current request if needed, writes the client-facing offer text, and calls `draft_counteroffer` with its reference, version, local date, time, and `client_text`. The backend checks the request, client eligibility and consent, past or unavailable times, and stores that exact text in a 30-minute draft without sending. A revised instruction replaces the draft. A clear plain YES while it is open is read by the model as a send and leads to `send_counteroffer`; a cancellation leads to `cancel_counteroffer`. Tool-loop sends and cancellations go through those stored-draft tools. The deterministic YES/NO offer hook, typed offer parser, closed-offer replies, and fixed counteroffer reply sentences are removed.
- **Calendar conversation.** The model interprets complete questions, status or count clarifications, follow-ups, and MORE from the owner's text and sent transcript, then calls `get_calendar` for current facts. It may read while a counteroffer draft waits; the draft stays open until sent, cancelled, replaced, or expired. The model should mention that draft and what a YES would send. A calendar read itself never approves, declines, or sends.
- **Pending-request decision.** Remaining owner wording enters the same tool loop. The model reads current requests before a decision, and the backend enforces their versions. The old #174 sent-question and #177 allowlist restrictions no longer gate this decision. A clear decision about one of several pending requests can use its reference and version; if the target is unclear, the model asks.
- **Failure and replay.** A tool error is returned to the model for a truthful final message. If the model or history fails, the fixed failure line is sent. The existing receipt and outbox path stores one response and replays it for a duplicate delivery.

## Owner calendar questions (#299)

The verified owner can ask by text what next week looks like, which clients are booked tomorrow, how many pending requests exist on Friday, or what else is on a page. The model interprets day, week, status, count, follow-up, and MORE wording using the business-local date, timezone, and sent-aware 24-hour owner transcript. It calls the strict JSON `get_calendar(from, to, statuses, offset)` read tool in the same loop as the #298 pending-request tools. The backend derives the business from the verified owner receipt and reads the current calendar and first-name client records for the requested local date range. It returns structured facts; the model writes the final SMS from those facts and must not present a read as a scheduling change.

- **Grounded scope.** The tool exposes only this business's current confirmed visits, unexpired pending requests, and unavailable blocks. Declined, cancelled, and expired records are omitted. Client names are first names only; no phone, address, notes, or other-client business data enters the result. The model can still misstate a count, date, or status in its prose; #299 accepts this residual risk rather than adding the old #285 per-entry owner draft checks.
- **Local dates and statuses.** `from` and `to` are interpreted in the business timezone. A local day spans midnight to midnight there; a block crossing midnight appears on both days but counts once in a total. Times include the appropriate PDT or PST abbreviation on a daylight-saving transition. The reply should name the requested date or range and label confirmed visits, pending requests that are not yet confirmed, and unavailable blocks separately. An unclear range or an ambiguous bare "bookings" count gets a focused question about the date or statuses before a tool read.
- **Follow-ups and MORE.** The model uses the preceding sent exchange to interpret "just the pending ones", "what about Friday?", "how many?", "by day", and "MORE". It supplies the resulting range, statuses, and page offset in each new tool call. The backend rereads the current calendar on every turn, including MORE, so an intervening approval, cancellation, expiry, or block edit is reflected. The old deterministic owner calendar matchers, `OWNER_QUESTION#<phone>` follow-up state, and stored paging fingerprint/cursor are removed; the transcript supplies conversational context. If a page changes between messages, the fresh result is authoritative, so a later page is not promised to match an earlier snapshot.
- **Open counteroffer.** A calendar read leaves the draft open. The model is told its current details and should remind the owner what a YES would send and how to cancel it; the draft's 30-minute expiry and send-time checks still apply. `get_calendar` itself cannot prepare, send, or cancel an offer.
- **Reply and replay.** The model writes one final owner SMS under the #298 GSM-7 and 480-septet rule, including its single rewrite on invalid output and fixed failure line on failure. There is no separate read-only owner drafter or per-entry date/time/reference validator. The existing receipt and outbox path stores the reply; a duplicate inbound message replays it without another calendar read or model call.

## Try it locally

For texts together with the owner web app on one shared calendar, use the text simulator described in the [README](../README.md#try-the-app-locally). The terminal exercise below has its own separate calendar.

With the backend dependencies installed as in the [README](../README.md#local-backend) and a local ignored `.env` containing `OPENAI_API_KEY`, run from the repository root:

```sh
(
  set -a
  source .env
  set +a
  cd backend
  .venv/bin/python -m scheduling.local_conversation
)
```

The subshell removes the key from the parent shell even if the command is interrupted. Use only invented messages. Recognizable phone numbers and entry/access-code phrases are rejected locally; this filter cannot detect every kind of private data.

1. As `client`, ask "Do you have anything tomorrow morning?" and reply with one of the offered times.
2. Type `/calendar` to see the pending request, then `/owner` and `yes`.
3. Switch back with `/client`, text "I can't make it tomorrow", and reply `yes`.
4. Type `/quit` to exit. The calendar and conversation memory reset on restart.

Without `OPENAI_API_KEY`, the simulator answers plain language with a question and a note; exact commands and replies to an existing offer still work.

## Profiles, privacy, and the cloud path

SMS collects only the visit date and time. The owner enters and verifies client profile fields (name, service address, and home size/duration) in the authenticated calendar. A text from a sender without an active, verified profile and matching consent is not authorized for commands. It gets no scheduling reply by SMS, the model is not called, and no scheduling change occurs. If the profile or consent changes after the text arrives, the conversation service refuses the text, and the sender recheck blocks delivery of its reply.

For a verified client, the model receives the inbound text, current business date and weekday, timezone, booking horizon, open prompt kind, up to eight short active references, the open calendar question's terms, and the bounded rolling 24-hour SMS transcript described below. System instructions stay separate from transcript text. It receives no profile name, phone, address, notes, or API key. A date-only reply to a booking invitation or earlier availability answer is interpreted using that transcript. Messages over 1,000 characters are rejected intact.

The persisted receipt and each accepted outbound send also create a body-free `SMS_HISTORY#` pointer keyed by verified client ID or owner phone and time. History reads query at most 64 recent pointers in that actor’s rolling 24-hour range and fetches the original records. A separate pointer fetches the latest eligible booking invitation. The final view keeps at most 24 whole messages within 12,000 characters, preserving the latest exchange and invitation when they fit. Older excess messages are omitted. Drafts and failed sends have no pointer. For read-only availability and client-calendar questions, the model's typed interpretation selects one backend read using the verified receipt's business and client. The backend checks dates, horizon, current openings, and visits, then returns its authoritative SMS answer. A long calendar list uses a compact form that still includes every current visit's full local start date, time, and status; pending means awaiting owner approval and not confirmed. The client reply drafter receives a bounded backend result: kind, local date/status facts with time and reference when available, machine reason where available, and the safe backend reply. This covers availability offers and date-only no-opening or horizon answers, calendar answers, and client cancel and reschedule questions or outcomes. It may write natural wording from those facts and the transcript. The backend accepts a draft only when it fits one GSM-7 segment and its explicit dates, times, and references exactly match those in the result. The model instructions ask it to keep each fact together, describe status accurately, and ask at most one question. The validator does not inspect status wording or the association among multiple facts, so a model-written contradiction remains possible. Enrique chose this minimal check to avoid rejecting sensible wording; malformed drafts and second-call failures use the deterministic safe reply (#283, 2026-10-08). No separate LLM validator is used. The first-call failure asks the client to try again later. Exact booking and confirmation replies keep their existing deterministic guards; an exact time sent after a booking invitation is offered like any other and needs the client's acceptance (#272, owner decision 2026-10-07). The model reads the acceptance and proposes `request_booking` naming the offered local date and time; the backend writes only if that instant is in the sender's own unexpired stored offer, creating the usual pending request with the receipt ID as idempotency key. Otherwise it offers current times. Plain YES and option numbers keep their existing deterministic matching ahead of the model.

The signed Twilio ingress can hand off a verified receipt ID to SQS after persisting it. The worker rereads the stored receipt, rechecks current consent and actor state, and uses the same conversation service as the local exercise, with the DynamoDB conversation memory above. Each SMS scheduling transaction checks STOP markers atomically with the calendar write. A cancelled transaction is terminal for that receipt, so a STOP that is later cleared cannot revive an older request. Offers, questions, and other noncommitted replies are recorded with a stable receipt-based outbox intent; the sender derives the destination from the verified receipt and rechecks consent, opt-out, and the fictional-number refusal. A committed client booking or cancellation already has an atomic template notification. After the write, the worker conditionally attaches the validated draft to that same pending client outbox item and stores its body on the receipt. If drafting fails, the worker crashes, or the outbox sender wins the race, that original notification remains the safe fallback; no second outbox item is made. The sender checks the appointment event version and current consent/opt-out before using an attached draft. Reply bodies are purged with inbound bodies 90 days after the last exchange (in the owner's own thread, 90 days after each message, #201). Duplicate webhook or queue delivery cannot create a second logical request or reply. Ingress never passes STOP, HELP, START, or UNSTOP texts to scheduling (the app's STOP words exclude CANCEL, so a bare "Cancel" is an ordinary message, matching dev's Twilio Advanced Opt-Out keywords, #91), but it honours a Twilio `OptOutType` of `START` only for the body START or UNSTOP, so a "Reply YES" answer is still read as an ordinary reply; a STOP or HELP provider tag always wins.

The AWS handoff is disabled by default. The `EnableSmsConversations` parameter only enables it when signed SMS ingress and SMS sending are also separately authorized; the worker obtains the OpenAI key from a `SecureString` at `/scheduling/<environment>/openai/api-key`. Enabling TTL on the table is part of the stack template. Deploying this code, provisioning that secret, and sending live texts require separate owner authorization.
